# 实例

六次走完闭环。每一例都点明症状、定位它的工具、改动，以及改动是**怎么被确认**的。

> **前置**：[度量闭环](00-methodology.md)。

## 怎么读这些例子

每例给四样东西，并且刻意不给第五样：

| 给出 | 为什么 |
| ---- | ------ |
| **症状** | 你实际会观察到什么 |
| **定位工具** | 哪个工具，以及它显示了什么 |
| **改动** | 那一处修改 |
| **确认方式** | 哪个工具，以及什么该发生变化 |

**不给加速数字。** 它取决于你的形状、平台与版本 —— 写在这里的数字会过期且具误导性，而你没有办法察觉。**确认那一步**才是可迁移的部分：在你自己的 kernel 上跑一遍，你就得到属于你的数字。

## 单机

### 例 1：编译器早就知道

**症状。** 一个 vector kernel 比它的算术量所暗示的更慢，而且在每种形状上都如此。

**定位。** 第 1 步 —— `<output_dir>/report/perf_hints.log` 里有一条 `PH001` `TileInnermostDimGranularity`。闭环再往下都没用上，而且那行 stderr 摘要在每次编译时都打印过。

**改动。** 调整 tile 形状，让最内维落在硬件搬运的粒度上。

**确认。** 该提示从 `perf_hints.log` 里消失。然后走第 2 步，看那一段是否真的变短 —— 提示是建议性的，所以它的消失只证明模式没了，不证明它曾经重要。

### 例 2：时间根本不在设备上

**症状。** 一个「本该很快」的 kernel 在 benchmark 循环里占了大头。

**定位。** 第 2 步 —— `stats.print_mean_tree(spread="stdev")` 显示分量落在 **host** span 而非 device。

**改动。** 别按次付 setup：把这些 program 注册到同一个 worker，并用 `pypto.runtime.DeviceTensor` 让不变的权重常驻。

**确认。** host span 变小、device span 不动。如果 device 时间也变了，说明还改了别的东西。

### 例 3：只是名字上融合

**症状。** 一个 matmul 接 bias 的 kernel，耗时大致等于两部分之和。

**定位。** 第 5 步 —— L2 swimlane 显示 cube 与 vector 的 span **首尾相接**而不是重叠。两个作用域、两次派发。

**改动。** 合成一个 `pl.at` 作用域并加 `optimizations=[pl.split(pl.SplitMode.UP_DOWN)]` —— [混合 kernel](../tutorials/03-mixed-kernel.md)。

**确认。** 还是看 swimlane：两段 span 现在应当重叠。预期还需要 `pl.cross_core_slot(slot_num=N)` —— 默认 8 槽的环装不下 `[128, 128]` FP32 的跨界 tile，编译时会明说。

### 例 4：并行的图，串行的执行

**症状。** 本该重叠的兄弟任务一前一后地跑。

**定位。** 第 5 步 —— `enable_dep_gen=True`，渲染出来的图在本该扇出的位置是一条链。OverlapMap 看到两个任务写同一张量的互不相交区域，而它无法证明不相交。

**改动。** 在能表达该断言的最窄范围上退出跟踪 —— `pl.at(..., no_dep_args=[t])` 优先于 `manual_dep=True`，后者优先于 `manual_scope`。

**确认。** 图变成扇出，**并且** swimlane 显示真正的重叠。两个都要看，因为图里扇出了、若某个环饱和了仍然会串行执行。

> **致命陷阱：** 每一种退出方式都是编译器无法检验的断言。如果那些区域其实并不互不相交，本例的「修复」就是一个偶发复现的竞态。

## 分布式

### 例 5：一个 rank 决定节奏

**症状。** 扩展到更多卡后收益停滞；每轮的平均时间几乎没改善。

**定位。** `per_rank("device")` —— 某个 rank 一直更慢，于是每次 collective 都在等它。单看 `per_round` 只会看到一个平坦的均值。

**改动。** 取决于成因，而本例的意义在于你现在知道该去看那个 rank：分片不均、该 rank 多做了 host 工作，或者它到得晚。

**确认。** `per_rank` 的离散度收窄。只有到那时，`per_round` 才值得优化。

### 例 6：collective 吃的是内存，不是时间

**症状。** 增加 rank 之后是分配失败，而不是变慢。

**定位。** 默认的 `mode="mesh"` 需要 **O(P)** 个窗口 —— 直接交换，每个对端一个窗口。

**改动。** `mode="ring"`：分块 reduce-scatter + allgather，**O(1)** 个窗口。

**确认。** 能分配出来了。然后看 `per_round` —— `ring` 要付 `2(P−1)` 个顺序步骤，所以在 rank 少或载荷小时它可能比被它替换掉的 `mesh` 更慢。要测，不要假设。

## 六例的共同规律

| 例 | 在哪一步被找到 |
| -- | -------------- |
| 1 | 1 —— 编译期提示 |
| 2 | 2 —— host / device 分野 |
| 3、4 | 5 —— 图与 swimlane |
| 5、6 | 分布式指标，先于任何调优 |

六例里有四例是在第 1、2、5 步——也就是便宜的那几步——被定位的。只有在这些之后，第 3 步的逐指令视角才值回它的成本。
