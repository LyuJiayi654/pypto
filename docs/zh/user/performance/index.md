# 性能优化

度量 → 定位 → 改动 → 确认，按这个顺序，单卡或多卡都一样。

> **前置**：[教程](../tutorials/index.md)，至少读到 [调度调优](../tutorials/05-scheduling-tuning.md)。

## 本章是什么

不是一份技巧清单，而是一个**闭环**：五个问题把差距收敛到单一原因，然后是一份手段目录——每条都写明代价，以及那个能让代码库保持诚实的东西：**怎么确认它生效**。

不管你有 1 个 rank 还是 64 个，这个闭环都一样；变的只是主导开销。

## 从哪开始

```text
                    00-methodology
                     （永远从这里）
                          │
            ┌─────────────┴─────────────┐
     01-single-node                02-distributed
      （单卡工作）              （多出：偏斜、collective）
            └─────────────┬─────────────┘
                     03-cases
```

**即使你自认为知道原因，也先读 `00-methodology`。** 它存在的全部意义就是拦住你去优化错的那一层——时间花在 host 上时调度优化毫无用处，而编译器已经标记出来的 tile 问题，再怎么调也补不回来。

## 本章不提供什么

**数字。** 这里没有任何一页会说「这样改快了 30%」，因为那个数字取决于你的形状、你的平台、你所在的版本——等你读到时它已经过期，而且过期得不易察觉。

每条手段真正携带的是**怎么确认它**：六个工具中的哪一个能看出改动生效了。这才是耐用的那一半。一个你在工具里看不见的加速，是一个半年后被人删掉时你无法辩护的加速。
